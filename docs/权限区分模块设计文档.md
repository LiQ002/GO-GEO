# 权限区分模块设计文档

> 版本：v1.0 ｜ 日期：2026-08-27
> 范围：admin 后台（:8001）、userconsole 企业工作台（:3000）、geoclient operator 端（:3001）的角色与权限区分，含交付人员代登录企业后台机制。

---

## 一、背景与目标

### 1.1 业务诉求

当前系统有三类使用者，但权限未做区分：

| 使用者 | 日常操作 | 登录入口 |
|---|---|---|
| 企业客户 | 查看数据报表、品牌看板 | userconsole :3000 |
| 交付人员 | 在 :3000 配置投稿、查收录、关键词、品牌词、图库、文章创作 | 需要进入企业后台 :3000 |
| 销售 / 管理员 | 管理企业、套餐、运营总览等 | admin :8001、operator :3001 |

现状是 userconsole 侧边栏 15 个菜单项对任何已登录企业账号**全部可见**，无法区分客户与交付人员；交付人员是平台账号，没有企业账号密码，**无法登录 :3000**。

### 1.2 设计目标

1. admin-roles（:8001/system/admin-roles）扩展为统一角色配置入口，支持两类角色：
   - **企业型角色**：绑定企业，仅 userconsole 页面权限。客户登录后只看到"数据报表 + 品牌看板"等指定页面。
   - **平台型角色**：交付人员 / 销售 / 管理员，可跨 admin + userconsole 配置权限。
2. 在 admin 企业管理（:8001/customers/enterprises）操作列新增"进入后台"按钮，让交付人员以**代登录**方式进入对应企业的 :3000，避免交付人员无法登录企业后台。
3. 不破坏现有 RBAC 鉴权与现有企业账号的默认行为（向后兼容）。

## 二、现状分析

### 2.1 现有 RBAC 体系（admin 后端 :8001）

数据表（`000001_identity_and_config.up.sql`）：

| 表名 | 用途 |
|---|---|
| `adm_users` | 平台账号 |
| `adm_roles` | 平台角色 |
| `adm_permissions` | 权限点（code/resource/action） |
| `adm_role_bindings` | 平台账号 ↔ 角色 |
| `adm_role_permissions` | 角色 ↔ 权限点 |

服务：`AdminRoleService`（[admin_role.proto](file:///d:/geo/kratos-svr/api/admin/v1/admin_role.proto)）、`AdminUserService`（admin_user.proto）。

鉴权（[authorization.go](file:///d:/geo/kratos-svr/app/admin/internal/server/authorization.go)）：gRPC operation → permission code 映射，校验 AdmUser 通过其角色拥有的权限点。

已初始化 12 个权限点（[000009_admin_permissions.up.sql](file:///d:/geo/kratos-svr/migrations/000009_admin_permissions.up.sql)）均为 **admin 端服务级**权限（dashboard.read、enterprise.manage、article.manage、system.rbac.manage 等），**不含 userconsole 页面级权限**。`super_admin` 角色拥有全部权限。

### 2.2 企业身份体系

[enterprise.go](file:///d:/geo/kratos-svr/internal/data/model/enterprise.go) 中 `Enterprise`（租户根）+ `EnterpriseAccount`（**单一全权限企业登录账号**，一企业一账号）。userconsole 登录主体是 `EnterpriseAccount`，与 `AdmUser` 是**两套独立身份系统**，token 不互通。

### 2.3 三套身份体系对比

| 身份 | 登录入口 | Auth 体系 | Token 类型 | 能访问系统 |
|---|---|---|---|---|
| 平台账号 AdmUser | admin :8001 / geoclient operator :3001 | `/api/admin/v1/auth/login` | admin token | :8001、:3001 |
| 企业账号 EnterpriseAccount | userconsole :3000 / geoclient client :3002 | `/api/user/v1/auth/login` | user token | :3000、:3002 |

> geoclient 通过 `NEXT_PUBLIC_APP_MODE` 区分 `operator`（:3001，admin token，平台人员桌面端 GEOHelper）与 `client`（:3002，user token，企业客户桌面端）。两者 auth 体系同各自 web 端一致。

核心矛盾：交付人员是 AdmUser，**没有企业账号密码**，无法直接登录 :3000 / :3002；但每日工作必须在 :3000 完成。

### 2.4 userconsole 侧边栏现状

[console-shell.tsx:216-254](file:///d:/geo/userconsole/src/components/console/console-shell.tsx) `navGroups` 硬编码 4 分组 15 项，对任何已登录企业账号全部可见：

- **概览**：工作台
- **内容资产**：品牌中心、企业知识、企业图库、关键词与问题、文章内容
- **增长执行**：内容投放、GEO 洞察、平台授权
- **企业管理**：数据报表、品牌看板、套餐与用量、我的订单、企业设置、实名认证

### 2.5 admin 前端现状

[enterprises/index.tsx:367-399](file:///d:/geo/admin/src/pages/enterprises/index.tsx) 企业列表操作列现有：详情、编辑、暂停/恢复。详情 Drawer 有：发起诊断、开通套餐、续费、加购额度、充值点数、调整套餐、调整配额、重置密码。**无"进入后台/代登录"入口**。

## 三、核心设计决策

### 决策 1：复用 `adm_roles` / `adm_permissions`，新增角色类型区分

在 `adm_roles` 增加 `role_type` 与 `enterprise_id`，不新建表，复用现有 CRUD 与 `adm_role_permissions` 关联表：

- `role_type='platform'`：平台型角色（交付人员 / 销售 / 管理员），`enterprise_id=NULL`
- `role_type='enterprise'`：企业型角色，`enterprise_id` 指向 `enterprises.id`

理由：用户明确要求在 admin-roles 页面统一配置；复用现有关联表，零迁移成本。

### 决策 2：扩展 `adm_permissions`，新增 userconsole 页面权限点

在 `adm_permissions` 新增 15 个 `console.*` 权限点（对应侧边栏 15 项），用 `resource='console'` 与 admin 端权限点区分，复用 `adm_role_permissions` 关联。

### 决策 3：企业账号 ↔ 角色绑定

`enterprise_accounts` 增加 `role_id`（nullable）：

- `role_id IS NULL` → **默认全权限**（向后兼容，现有企业账号不受影响）
- `role_id = X`（企业型角色）→ 按角色 console.* 权限过滤侧边栏

> EnterpriseAccount 当前是一企业一账号，单 `role_id` 足够；未来若一企业多账号多角色，再升级为 `ent_account_role_bindings` 多对多表。

### 决策 4：交付人员进入 :3000 用"代登录"机制（非统一登录）

平台型角色访问 userconsole 不走统一登录，而通过 admin 企业管理页"进入后台"按钮**代登录**：

- **数据归属** = 选中企业
- **可见页面** = 交付人员平台型角色被授予的 `console.*` 权限（内容资产 + 增长执行类，而非企业的"数据报表 + 品牌看板"）

这使交付人员与企业客户在同一 :3000 上**权限互斥、自然区分**：客户只看报表，交付人员只看运营。

```protobuf
rpc ListEnterpriseRoles(ListEnterpriseRolesRequest) returns (ListEnterpriseRolesReply) {

}
```

### 5.2 代登录接口（admin 服务 EnterpriseService）

新增 RPC，签发带企业上下文 + 交付人员角色权限的 user-console token：

```protobuf
rpc IssueEnterpriseConsoleToken(IssueEnterpriseConsoleTokenRequest)
    returns (IssueEnterpriseConsoleTokenReply) {
  option (google.api.http) = {
    post: "/api/admin/v1/enterprises/{enterprise_id}/console-token"
    body: "*"
  };
}

message IssueEnterpriseConsoleTokenRequest {
  uint64 enterprise_id = 1;
  string reason = 2;        // 操作原因，写审计
}
message IssueEnterpriseConsoleTokenReply {
  string access_token = 1;
  string refresh_token = 2;
  uint64 enterprise_id = 3;
  string ticket = 4;        // 一次性 ticket，userconsole 用此兑换
}
```

**鉴权映射**（[authorization.go](file:///d:/geo/kratos-svr/app/admin/internal/server/authorization.go)）：

```go
services := []struct{ prefix, permission string }{
    // ...
    {"/admin.v1.EnterpriseService/IssueEnterpriseConsoleToken", "enterprise.console.impersonate"},
}
```

**实现要点**：

1. 校验调用者是 AdmUser 且拥有 `enterprise.console.impersonate`。
2. 校验目标企业存在且 status 正常。
3. 取调用者角色（adm_role_bindings → adm_roles），取其 `console.*` 权限集。
4. 签发 user-console 体系 token（复用 `/api/user/v1/auth/login` 同一套签发逻辑），claims 额外标注：
   - `enterprise_id` = 目标企业
   - `impersonator_admin_id` = 调用者 AdmUser ID
   - `acting_role_id` = 交付人员角色 ID
   - `session_kind = "impersonation"`
5. 生成一次性 `ticket`（30s 过期，存 Redis 或 DB 短表），ticket 与 token 绑定。
6. 写审计日志（`audit_logs`）。

### 5.3 ticket 兑换接口（user 服务侧新增）

userconsole 无法直接信任 admin 签发的 token（跨服务），用 ticket 一次性兑换：

```protobuf
// api/user/v1/auth.proto
rpc ExchangeImpersonationTicket(ExchangeImpersonationTicketRequest)
    returns (ExchangeImpersonationTicketReply) {
  option (google.api.http) = {
    post: "/api/user/v1/auth/exchange-ticket"
    body: "*"
  };
}

message ExchangeImpersonationTicketRequest {
  string ticket = 1;
}
message ExchangeImpersonationTicketReply {
  string access_token = 1;
  string refresh_token = 2;
  uint64 enterprise_id = 3;
  bool is_impersonation = 4;
}
```

实现：校验 ticket 有效且未用过 → 标记已用 → 返回 token。ticket 可由 admin 服务签发后写入共享存储（Redis / DB），user 服务读取。

### 5.4 userconsole profile 返回权限

[console-data-provider.tsx](file:///d:/geo/userconsole/src/components/console/console-data-provider.tsx) 取 profile 的接口（user 服务）扩展返回 `permissions`：

```protobuf
message ProfileReply {
  // ...existing fields...
  repeated string permissions = N; // 如 console.brand, console.geo
  bool is_impersonation = N1;      // 是否代登录会话
  string impersonator_name = N2;   // 代登录人姓名（供提示条显示）
}
```

**逻辑**：

- 普通企业登录：`permissions` 取自 `enterprise_accounts.role_id` 的 `console.*` 权限；`role_id IS NULL` → 返回全部 console.*（兼容）。
- 代登录会话（claims 有 `acting_role_id`）：`permissions` 取自该角色的 `console.*` 权限，**企业上下文取自 claims 的 `enterprise_id`**。

```tsx
async function onEnterConsole(record) {
  Modal.confirm({
    title: '进入企业后台',
    content: `将以「${record.name}」身份进入 GEOHelper 企业工作台，操作会记入审计日志。`,
    onOk: async () => {
      const { ticket } = await enterpriseServiceIssueConsoleToken({
        enterpriseId: record.id,
        reason: '交付人员代登录',
      });
      // 新窗口打开，避免弹窗拦截提示手动复制
      const url = `${USERCONSOLE_ORIGIN}/auth/impersonate?ticket=${ticket}&enterpriseId=${record.id}`;
      window.open(url, '_blank') || copyToClipboard(url);
    },
  });
}
```

## 八、角色配置模板

### 8.1 企业客户默认角色（企业型）

- `role_type='enterprise'`，`enterprise_id` 绑定具体企业（或用模板角色多企业复用）
- 权限点：`console.dashboard`（工作台，必给）、`console.dashboard_data`（数据报表）、`console.brand_board`（品牌看板）
- 企业账号 `enterprise_accounts.role_id` 指向它

### 8.2 交付人员角色（平台型）

- `role_type='platform'`，`enterprise_id=NULL`
- console.* 权限：`console.dashboard`、`console.brand`、`console.knowledge`、`console.gallery`、`console.keywords`、`console.articles`、`console.publishing`、`console.geo`、`console.authorizations`、`console.realname`
- admin 端权限：`enterprise.console.impersonate`（代登录）、`enterprise.read`（看企业列表）、可选 `dashboard.read`
- 在 admin-users 中给交付人员 AdmUser 绑此角色

> 交付人员**不需要**企业客户那两个权限（dashboard_data / brand_board），反之亦然——权限点互斥，天然实现"客户只看报表，交付人员只看运营"。

### 8.3 销售 / 管理员角色（平台型）

- `role_type='platform'`，`enterprise_id=NULL`
- admin 端权限：按职责配置（销售可给 enterprise.manage / sales.*；管理员给 system.rbac.manage 等或直接用 super_admin）
- 是否需要 console.* 权限视是否需代登录 :3000 而定

## 九、完整业务流程

### 9.1 企业客户登录

1. 企业客户在 :3000/login 用企业账号凭据登录。
2. `/api/user/v1/auth/login` 签发普通 user token。
3. profile 接口取 `enterprise_accounts.role_id` 的 console.* 权限（数据报表 + 品牌看板 + 工作台）。
4. 侧边栏仅显示企业管理分组中的"数据报表""品牌看板"及"工作台"。
5. 企业客户也可用同一 user token 登录 geoclient client 桌面端（:3002），权限过滤规则一致（如桌面端侧边栏同样按 console.* 过滤）。

### 9.2 交付人员代登录

1. 管理员在 admin-users 创建交付人员 AdmUser，绑"交付人员"平台型角色。
2. 交付人员用 AdmUser 凭据登录 :8001。
3. 在企业管理页面对企业 X 点"进入后台"，二次确认。
4. admin 后端 `IssueEnterpriseConsoleToken` 校验权限，签发带 `enterprise_id=X` + `acting_role_id=交付人员角色` 的 token，生成一次性 ticket。
5. 新窗口打开 :3000/auth/impersonate?ticket=xxx。
6. userconsole 用 ticket 调 `/api/user/v1/auth/exchange-ticket` 换 token，写 cookie，跳工作台。
7. profile 识别代登录会话 → 侧边栏按交付人员角色的 console.* 权限显示（品牌 / 知识 / 图库 / 关键词 / 文章 / 投放 / GEO / 授权）。
8. 所有数据操作归属企业 X。
9. 顶部显示代登录提示条，可随时退出。

### 9.3 平台人员访问 admin / operator

- 交付人员 / 销售 / 管理员用 AdmUser 凭据登录 :8001 与 operator(:3001)，按各自平台型角色的 admin 端权限点访问 admin 模块。无需特殊机制。

## 十一、风险与安全

1. **代登录审计**：每次 `IssueEnterpriseConsoleToken` 写审计日志，含操作人、目标企业、原因、时间，便于追溯。
2. **ticket 一次性**：30s 过期、用后即焚，避免 token 泄露在 URL / referer。
3. **权限点互斥**：企业型角色只能选 console.*，平台型可选全量，UI 层过滤防止误配。
4. **向后兼容**：`enterprise_accounts.role_id IS NULL` 默认全权限，现有企业账号不受影响；逐步为存量企业绑定"企业客户默认角色"。
5. **代登录提示**：userconsole 顶部常驻提示条，防止交付人员误以为是自己账号操作。
6. **跨域 cookie**：admin(:8001) 与 userconsole(:3000) 端口不同，生产环境若不同域名需配 cookie SameSite / 跨域；本文用 ticket 兑换 + 各自 set-cookie 规避直接跨域传 token。

## 十二、待确认问题

1. **代登录企业范围**：交付人员能代登录所有企业，还是只能代登录分配给他的企业？后者需建 `adm_operator_enterprises` 分配表，更安全但多一张表。
2. **企业客户角色模板化**：是否所有企业都只看"数据报表 + 品牌看板"？若是，用一个名为"企业客户-只读报表"的企业型角色作模板，所有企业账号 role_id 都指向它即可，省配置；若需每企业定制，则每企业一个角色。
3. **桌面端权限区分（operator :3001 / client :3002）**：交付人员用 operator 端（admin token）、企业客户用 client 端（user token）。是否需要按角色控制桌面端功能？还是桌面端保持全功能、仅靠各自 token 登录即可？代登录签发的 user token 是否可用于 client 桌面端（交付人员以企业身份用 client 桌面端工作）？
4. **存量企业迁移**：现有企业账号是否需一次性批量绑定"企业客户默认角色"，还是保持 NULL（全权限）逐步收敛？

确认以上 4 点后即可进入 P0 实施。
