## 二、修复明细

### 问题 1：客户端成功率重复乘 100

**根因**：`client.ts` 的 `getUserStats()` 已将小数换算成百分数（0-100），而 `Dashboard.tsx` 又乘了一次 100，导致 0.83 → 83 → 8300%。运营端 `operator.ts` 返回小数 0-1、Dashboard 乘 100，逻辑正确，故以运营端语义为准统一。

**改动**：
- [geoclient/lib/api/client.ts](file:///d:/geo/geoclient/lib/api/client.ts) — `successRate` 由 `Math.round((success/attempts) * 100)` 改为 `success / attempts`（返回 0-1 小数），与运营端一致。

**验证**：`Dashboard.tsx` 中 `Math.round((stats?.successRate ?? 0) * 100)` 现在得到正确的百分数。

### 问题 3：运营端「最近活动」无数据

**根因**：前端把 `dashboard.alerts` 当作 `recentActivity`；后端只查 `alerts` 表 `status='open'` 记录，但**全工程无任何写入 alerts 表的代码**（无 Create/Raise），表恒为空。真实活动数据在 `pub_tasks` 等表未被使用。

**改动**：
- [data/dashboard.go](file:///d:/geo/kratos-svr/app/admin/internal/data/dashboard.go) — 新增最近活动查询：从 `pub_tasks`（JOIN `cnt_article_snapshots`→`cnt_articles` 取标题、JOIN `cfg_publish_channels` 取平台名）取最近 10 条，按 status 映射 `success/failed/started`，组装中文消息如「《标题》发布到 微信公众号 成功」。
- [dashboard.proto](file:///d:/geo/kratos-svr/api/admin/v1/dashboard.proto) / [biz/dashboard.go](file:///d:/geo/kratos-svr/app/admin/internal/biz/dashboard.go) / [service/dashboard.go](file:///d:/geo/kratos-svr/app/admin/internal/service/dashboard.go) — 新增 `DashboardActivity` 消息与 DO、透传。
- [operator.ts](file:///d:/geo/geoclient/lib/api/operator.ts) — `getStats()` 改从 `dashboard.activities` 映射 `recentActivity`（原先读 `alerts`）。

> 说明：`alerts` 字段保留不变（仍用于告警区块，若有告警写入未来可复用）。

### 问题 4：用户管理「文章数/发布数/发布率」无数据

**根因**：
- Proto `EnterpriseDetail` 无统计字段。
- 前端 `mapEnterprise` 用 `quotaUsage()` 从配额 `usedValue` 取值作为 articleCount/publishedCount，但后端 `reserveQuota` 只累加 `reserved_value`，**全工程无 commit 操作把 reserved 转入 used_value**，导致 `used_value` 恒为 0。
- 无任何 SQL COUNT 聚合文章/发布数。

**改动**：
- [enterprise.proto](file:///d:/geo/kratos-svr/api/admin/v1/enterprise.proto) — `EnterpriseDetail` 新增 `article_count`(5)、`published_count`(6)。
- [biz/enterprise.go](file:///d:/geo/kratos-svr/app/admin/internal/biz/enterprise.go) — `EnterpriseDetail` DO 增加 `ArticleCount`、`PublishedCount`。
- [data/enterprise.go](file:///d:/geo/kratos-svr/app/admin/internal/data/enterprise.go) — `hydrate()`（List 与 Get 共用）新增 COUNT 聚合：`SELECT enterprise_id, COUNT(*) AS total, SUM(CASE WHEN status='published' THEN 1 ELSE 0 END) AS published FROM cnt_articles GROUP BY enterprise_id`，回填到各 detail。
- [service/enterprise.go](file:///d:/geo/kratos-svr/app/admin/internal/service/enterprise.go) — `enterpriseDetailDTO` 透传 `ArticleCount`、`PublishedCount`。
- [operator.ts](file:///d:/geo/geoclient/lib/api/operator.ts) — `mapEnterprise` 改为直读 `detail.articleCount`/`detail.publishedCount`；删除已无用的 `quotaUsage()`。发布率由前端 `Users.tsx` 用 `publishedCount/articleCount*100` 计算（已有逻辑，现在数据真实）。

### 问题 5：文章管理发布状态一直显示「待发布」

**根因（核心）**：后端将文章标记为 `published` 的唯一路径在 [worker_execution.go:258](file:///d:/geo/kratos-svr/app/admin/internal/data/worker_execution.go)：
```go
if taskStatus == "succeeded" && resultURL != "" { ... status: "published" ... }
```
`resultURL` 由 `publishResultIdentifiers(input.ResultJSON)` 解析，只识别顶层 `publishedUrl` 字段。但前端 [Publishing.tsx](file:///d:/geo/geoclient/components/pages/operator/Publishing.tsx) 上报的 `result` 只含 `jobId/taskId/enterpriseId/articleId/results`，**从未发送顶层 `publishedUrl`**（实际值嵌在 `results[].publishedUrl`），导致 `resultURL` 恒为空 → 文章永远停在 `normal` → 前端 `mapArticleStatus("normal")` 兜底为 `pending`（待发布）。

**改动**：
- [Publishing.tsx](file:///d:/geo/geoclient/components/pages/operator/Publishing.tsx) — 上报 `result` 增加顶层 `publishedUrl`（取首个成功平台的 `publishedUrl`）与 `platformArticleId`。**此为根因修复**：发布成功后后端会将文章状态置为 `published`。
- [Articles.tsx](file:///d:/geo/geoclient/components/pages/operator/Articles.tsx) — 状态过滤下拉框枚举对齐后端：`pending_review/normal/published/disabled/archived`（原先用 `pending/partial/published/failed`，除 `published` 外后端精确匹配均不命中）。
- [admin/src/utils/platform-enums.ts](file:///d:/geo/admin/src/utils/platform-enums.ts) — `articleWorkflowStatusOptions` 补充 `published`、`archived` 选项（原先缺失，已发布文章在 admin 端会显示英文 `published`）。

> `mapArticleStatus` 无需改动：`published`→已发布、`normal`→待发布（审核通过待发布，语义正确）。修复根因后，已发布文章将正确显示「已发布」。

## 五、上线注意事项

1. **无需数据库迁移**：本次仅新增聚合查询，未新增表或字段；`pub_tasks.publish_channel_id`、`cfg_publish_channels`、`cnt_articles.status` 等均已有。
2. **数据即时生效**：各平台统计、最近活动、用户文章数均为实时聚合查询，部署后立即有数据（前提是已有发布任务/文章数据）。
3. **历史文章状态**：问题 5 修复后，**新发起的发布任务**成功上报后会正确置为 `published`；历史已发布但状态仍为 `normal`/`pending_review` 的文章不会自动回填，如需修正可执行一次性 SQL（注意：`pub_tasks.result_url` 历史数据为空，回填不应依赖该字段）：
   ```sql
   UPDATE cnt_articles a
   JOIN (
     SELECT s.article_id, MIN(t.completed_at) AS first_published_at
     FROM pub_tasks t
     JOIN cnt_article_snapshots s ON s.id = t.article_snapshot_id
     WHERE t.status = 'succeeded'
     GROUP BY s.article_id
   ) p ON p.article_id = a.id
   SET a.status = 'published', a.published_at = p.first_published_at, a.version = a.version + 1
   WHERE a.status <> 'published';
   ```
   （执行前请备份并核对快照-文章关系。）
4. **前端重启要求**：`Publishing.tsx` 的修改（添加顶层 `publishedUrl`）需要前端重新构建或重启开发服务器才能生效。若未重启，新发布成功后文章状态仍不会自动变为 `published`，需再次执行上述回填 SQL。
4. **既有测试失败**：`zhihu/publish.test.ts` 的 `page.$$eval` mock 问题与本次无关，建议另行修复测试 mock。
5. **客户端 legacy 类型**：`openapi.d.ts` 中 `PublishStatsOut` 暂未含 `platform_stats`（legacy openapi.json 未同步），前端以类型断言兼容；运行时 JSON 已包含该字段，功能正常。如需类型精确，可后续更新 `geoclient/openapi.json` 中 `PublishStatsOut` schema 后重跑 `pnpm api:generate:legacy`。
